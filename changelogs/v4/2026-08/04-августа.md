## Новая система радиусов: concentric radius

Вместо статичной таблицы радиусов по размерам компонентов добавлена формула `radius_child = radius_parent - gap` через CSS custom property `--radius-outer` (зарегистрирован через `@property` для анимируемости). Результат ограничен снизу значением `--radius-mini` (2px) через `clamp()`, чтобы большой отступ не убирал скругление совсем — но если у родителя явно установлен `--radius-outer: 0` («без радиуса»), это ограничение не применяется и 0 остаётся 0 (доверяем явному выбору автора). `Pagination` мигрирован на новый механизм как первый реальный пример (визуально не изменился). Добавлена документационная Storybook-история `Foundations/Radius` с интерактивным примером и разбором формулы.

Зачем: устраняет источник рассинхрона, когда скругление контейнера и вложенного элемента подбираются вручную и независимо друг от друга (пример — `Pagination`, где `+4px` в радиусе и `padding: 4px` были одним и тем же числом, продублированным без связи). Часть архитектурного рефакторинга v4 (`ARCHITECTURE-V4.md`, `.claude/rules/radius.md`), Linear T-164.

## Юнит-тесты для формулы concentric radius

Формула конкретно скругления (`floor` + доверие явному «без радиуса») вынесена из Storybook-истории в `NumberUtils.concentricRadius` (`src/utils/NumberUtils.ts`) и покрыта пятью юнит-тестами (`vitest/numberUtils.test.ts`) — по одному на отдельный механизм: обычный случай, срабатывание floor, явный 0 (не поднимается до floor), радиус уже ниже floor, кастомный floor.

Зачем: сама CSS-формула (`clamp()`/`@property`) не тестируется юнит-тестами — jsdom не резолвит `calc()`/`clamp()` по-настоящему, это задача Cypress/визуальных тестов. Но JS-версия той же формулы — чистая функция с реальными граничными случаями, которую стоило вынести в переиспользуемое место и закрепить тестами, а не оставлять недокументированной логикой внутри демо-истории.

## Семантические роли для отступов (spacing)

Добавлен слой семантических ролей поверх уже существующей примитивной шкалы отступов (`--narrow-gap` … `--xxl-gap`): `--space-inline`, `--space-stack`, `--space-content`, `--space-section`, `--space-inset-compact`, а также матрица control-ролей по размеру `--space-control-{x,y}-{mini,s,m,l,xl}` (`_spacing.scss`, ранее не подключённый файл — теперь реально используется через `@use`). `DataGrid`, `NavigationList` (header/footer) и `Tabs.Item` переведены на новые роли как реальный пример (без изменения итоговых пикселей). Добавлена документационная Storybook-история `Foundations/Spacing`.

Осознанно не входит в эту итерацию: массовая миграция оставшихся ~100 мест с хардкодом px (это точечная работа по каждому компоненту, не механическая замена) и перевод конкретных компонентов (`Button`, `TextInput`) на control-role матрицу — их текущие значения по размерам не совпадают с сид-значениями матрицы и требуют дизайн-решения. Также не решён вопрос снапа `--s-gap` (6px) на 4px-сетку — он влияет на публичный проп `gap="s"` у `Flex`/`Grid`.

Зачем: устраняет ситуацию, когда одинаковые по смыслу отступы (например, вертикальный ритм между полями формы) выбираются в разных компонентах независимо и хардкодом, без общего названия и источника правды. Часть архитектурного рефакторинга v4 (`ARCHITECTURE-V4.md`, `.claude/rules/spacing.md`), Linear T-165.

## Семантическая роль elevation (z-index + shadow)

Добавлены токены `--elevation-{flat,raised,sticky,overlay,modal,toast}-{z-index,shadow}` (`_elevation.scss`), связывающие конкретный уровень z-index с конкретной комбинацией теней под одним именем. Маппинг не придуман с нуля — `raised`/`overlay`/`modal`/`toast` реверс-инжинирены из комбинаций теней, которые уже независимо совпадали у нескольких реальных компонентов (например, `Popover`, `Drawer` и `Toolbar.Group` все использовали ровно `shadow-1`+`shadow-4`). На новые роли переведены (без изменения итоговых пикселей): `DataTable` column headers, `Tabs.Item`/`DatePicker` day/`BottomNavigation` item/`Range` track, `Popover`/`Drawer`/`Toolbar.Group`, `Modal`, `Toast`. Добавлена документационная Storybook-история `Foundations/Elevation`.

Осознанно не входит в эту итерацию: `NavigationList`/`BottomNavigation` (внешняя поверхность, не пункты) сейчас используют вес тени как у Modal, хотя это постоянный chrome, а не оверлей — не мигрированы, т.к. понижение веса тени изменит внешний вид, а решение не подтверждено. Тёмная тема для теней (`--shadow-*` почти не видны на тёмной поверхности) также не реализована — нужно отдельное дизайн-решение в духе Material 3 tonal elevation.

Зачем: устраняет ситуацию, когда z-index и тень для одного и того же смыслового уровня («это оверлей», «это модалка») подбираются раздельно и независимо, из-за чего одинаковые по смыслу элементы могут визуально разъезжаться. Часть архитектурного рефакторинга v4 (`ARCHITECTURE-V4.md`, `.claude/rules/elevation.md`), Linear T-166.

## Тени для тёмной темы + исправлен вес тени NavigationList/BottomNavigation

`--shadow-*` получили dark-theme override (`_shadow.scss`, под `[data-altrone-root='true'][data-altrone-theme='dark']`). Слои-обводки на `--gray-aN` менять не потребовалось — в тёмной теме `--gray-aN` уже светлый оверлей (см. `colors/_gray.scss`), поэтому автоматически читается как хайлайт. Слои размытия на `--black-aN` сдвинуты примерно на 4 шага по шкале alpha (например, `--black-a1` → `--black-a5`) — обычный чёрный на непрозрачности светлой темы почти не виден на уже тёмной поверхности. Это первый проход по реальным числам, не финальный дизайн — более «правильное» решение в духе Material 3 tonal elevation (менять светлоту самой поверхности, а не полагаться на тень) отложено до появления материалов `Box`.

Также: внешняя поверхность `NavigationList`/`BottomNavigation` переведена с `shadow-1`+`shadow-5` (вес Modal) на `--elevation-raised-shadow` — как и было предположено в открытом вопросе T-166, теперь подтверждено и сделано. Это единственное изменение в рамках elevation, которое реально меняет отрисовку (не zero-diff).

Зачем: закрывает оба открытых вопроса, оставленных в T-166 — оба требовали дизайн-решения, которое теперь принято. Часть архитектурного рефакторинга v4 (`ARCHITECTURE-V4.md`, `.claude/rules/elevation.md`), Linear T-166.

## Усилен рецепт теней для тёмной темы

По скриншоту стало видно, что первый проход (сдвиг только `--black-aN` слоёв примерно на 4 шага) практически не читается — свотчи ролей elevation почти сливались с фоном. Причина: `--background-1` и `--background-2` в тёмной теме близки по светлоте между собой, так что тени приходится делать основным сигналом глубины, а не вспомогательным. Усилил рецепт: слои-обводки на `--gray-aN` тоже теперь сдвигаются (примерно на 3 шага, а не остаются как есть), слои размытия на `--black-aN` — заметно сильнее, чем раньше (примерно на 6-8 шагов вместо 4, например `--black-a1` → `--black-a7`).

Зачем: первая версия дизайн-решения оказалась недостаточной на практике — визуальная проверка обнаружила, что тени не читаются. Часть архитектурного рефакторинга v4 (`ARCHITECTURE-V4.md`, `.claude/rules/elevation.md`), Linear T-166.
