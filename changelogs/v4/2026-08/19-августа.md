## Хуки для адаптивности: useBreakpoint / useContainerQuery

Добавлены два React-хука для двухуровневой модели адаптивности. `useBreakpoint()` — пять булевых флагов `is{Xs,Sm,Md,Lg,Xl}` (каждый — `min-width`), зеркалящих значения `--breakpoint-*` из CSS; построен поверх уже существующего `useMediaMatch`, поэтому SSR-safe (false до монтирования, без рассинхрона с сервером). `useContainerQuery(ref, { minWidth?, maxWidth? })` — то же самое, но по размеру конкретного элемента, а не вьюпорта: нужен для структурной адаптивности (например, схлопывание List-Detail в одну панель), которую нельзя выразить чистым CSS `@container`. Построен на новом `useElementSize(ref)` (обёртка над `ResizeObserver`), который тоже SSR-safe — до измерения на монтировании возвращает `{width: 0, height: 0}`, сервер и первый клиентский рендер всегда совпадают.

Добавлена документационная Storybook-история `Foundations/Responsiveness` с живыми примерами обоих хуков.

Зачем: JS-уровень адаптивности до этого не имел SSR-safe инструментов вообще — либо руками писать `window.matchMedia`/`ResizeObserver` с риском рассинхрона гидратации, либо не делать структурную адаптивность вовсе. Часть архитектурного рефакторинга v4 (`ARCHITECTURE-V4.md`, `.claude/rules/responsiveness.md`), Linear T-171.

## Application/Screen: базовый API (breaking change)

`AltroneApplication` стал чистым корнем-провайдером (тема, локаль, конфиг, диалоги, тосты) — больше не рендерит `<Screen>` внутри себя и не владеет пропами `sidebar`/`header`. Мёртвые CSS-классы, существовавшие только ради старого layout (`.Application_withSidebar`, `.Sidebar`, `.ApplicationMain`, `.ApplicationHeader`, `.ApplicationContent`), удалены вместе с ним.

`Screen` переписан на namespace-API: `Screen.Header`/`Screen.Sidebar`/`Screen.Content`/`Screen.Footer` — зоны, которые потребитель кладёт в `children` в любом порядке; CSS-грид (`grid-template-areas` + `:has(> .Sidebar)`) сам расставляет их по позиции независимо от порядка в JSX. Не отрендеренная зона просто отсутствует в сетке — булевого пропа видимости и внутреннего контекста для этого не нужно (старый `Screen.context.ts`/`useScreenSidebar` убран — снаружи `Screen.tsx` его никто не использовал). Добавлен проп `size` (`mini/s/m/l/xl`), ограничивающий ширину `Screen.Content` — значения переиспользуют уже существующие токены `--breakpoint-*`, не изобретены заново.

Попутно исправлен реальный хак в старом CSS: сайдбар был `position: fixed` с ручным `margin-left`/`calc(100vw - Npx)` на колонке контента, причём захардкоженная ширина сайдбара не совпадала между двумя местами (300px в одном, 320px в другом). Настоящая grid-колонка убирает необходимость в этом расчёте вообще. `Screen.Header` переведён на `--elevation-sticky-*` — он уже был обозначен как кандидат на эту роль в `elevation.md`, просто до сих пор не мигрировал, так как `Screen` не трогали.

Добавлены юнит-тесты (`vitest/screen.test.tsx`) и переписана Storybook-история `Components/Containers/Screen`: пустой `Screen` (`Screen.Content` без остальных зон — как и просили для этого прохода), составление зон с живым включением/выключением через `Switcher`, и демонстрация влияния `size` на ширину контента.

Пресеты (`Screen.ListDetail`, `.Dashboard` и т.д.) в этот проход не входят — по решению, отдельная задача после базового API.

Зачем: переход от «собери экран руками из примитивов» к «опиши экран через компоненты» — с прицелом на будущие пресеты и на то, чтобы переключение между экранами было заботой потребителя (свой роутер/state), а не библиотеки. Часть архитектурного рефакторинга v4 (`ARCHITECTURE-V4.md`, `.claude/rules/application-screen.md`), Linear T-172.

## Toolbar: экшены для шапки экрана (Back/Search/SidebarToggle/BackForward)

Добавлены четыре готовых экшена на `Toolbar`, спроектированных под типовые контролы шапки приложения: `Toolbar.BackAction` (одиночная icon-кнопка «назад»), `Toolbar.SearchAction` (одиночная icon-кнопка поиска), `Toolbar.SidebarToggleAction` (icon-кнопка, меняет иконку/лейбл по контролируемому пропу `collapsed` — тот же булев стейт, что уйдёт в `Screen.Sidebar.collapsed`), `Toolbar.BackForwardAction` (парный сегмент-контрол в духе браузера/macOS, каждая половина независимо кликабельна и дизейблится). Все четыре полностью контролируемые и не хранят состояние — тот же паттерн, что уже принят у `Checkbox`/`Switcher`/`Range`. Живут на `Toolbar`, не на `Screen`, так как это общие концепции тулбара, а не специфика конкретного компонента.

Тексты подписей взяты не хардкодом, а через новый locale-namespace `toolbar` (`back`/`forward`/`search`/`collapseSidebar`/`expandSidebar`), добавленный во все пять словарей (`en`/`ru`/`fr`/`ge`/`sp`).

Добавлена новая история `Components/Containers/Toolbar → Header Actions` с живой демонстрацией всех четырёх экшенов, и юнит-тесты (в `vitest/toolbar.test.tsx`) на доступное имя кнопок, переключение `SidebarToggleAction` по `collapsed` и независимое отключение половин `BackForwardAction`.

Заодно нашли и починили баг: единственная история в проекте (`Screen.stories.tsx`), обходившая общий `StorybookDecorator` и хардкодившая свой `<AltroneApplication accent="blue">`, из-за чего тулбар-переключатели темы/акцента/языка в Storybook на неё не действовали — переведена на `StorybookDecorator`, как и все остальные истории. Также список акцентных цветов в `.storybook/preview.ts` не включал `green`/`orange`, добавленные в T-167/T-168 — дополнен до всех 10.

Зачем: закладывает API для будущего `Screen.Header` (и в перспективе — пресетов) без единого байта состояния или логики внутри самого `Toolbar`, полностью в духе «Screen отвечает только за расположение». Часть архитектурного рефакторинга v4 (`.claude/rules/application-screen.md`), Linear T-172.

## Все 8 пресетов Screen: ListDetail, Dashboard, Form, Settings, DataView, Auth, Empty, Error

Реализованы все 8 пресетов из решённого ранее списка. Каждый `Screen.X` рендерит полноценный `<Screen>` внутри — единый ментальный шаблон для всех восьми, а не смесь «одни полноэкранные, другие — фрагменты для Content». `ListDetail`/`Dashboard`/`Form`/`Settings`/`DataView` принимают `Screen.Header`/`Screen.Sidebar`/`Screen.Footer` как children, точно как обычный `Screen`. Реализация почти целиком через CSS-модификатор, который трогает только `.Content` (grid для Dashboard, центрирование для Form, edge-to-edge для DataView, общий `.Centered` для Auth/Empty/Error) — раскладка Header/Sidebar/Footer не меняется ни в одном пресете. `Settings` вообще не потребовал новой CSS — это `Screen` с дефолтным `size="s"`. Единственное исключение — `ListDetail`: `list`/`detail` сделаны пропами, а не zone-компонентами, так как это всегда обязательная пара, в отличие от опциональных Header/Sidebar/Footer (и чтобы не парсить children по типу, по прецеденту `Toolbar`).

Каждый файл пресета импортирует `Screen` напрямую из `Screen.tsx`, а `Screen.tsx` подключает все 8 через баррель `./components` для namespace — это создаёт циклический импорт. Проверено не только тайпчеком, но и реальным рендером через юнит-тесты (`vitest/screenPresets.test.tsx`) — работает корректно, так как `Screen` используется только внутри тела функций, не на верхнем уровне модуля.

Пресеты не хранят собственный дефолтный контент: `Empty`/`Error` не рендерят fallback-текст сами — за это отвечает уже существующий атом `Empty` (`core/src/components/empty/`), который и предполагается класть внутрь `Screen.Empty`/`Screen.Error` как обычный children, без дублирования этой ответственности на уровне Screen.

Добавлены 8 отдельных Storybook-историй — по одной на пресет (`Components/Containers/Screen/ListDetail`, `/Dashboard`, `/Form`, `/Settings`, `/DataView`, `/Auth`, `/Empty`, `/Error`), каждая с реалистичной композицией из существующих компонентов библиотеки (`NavigationList`, `Toolbar`, `Form`, атом `Empty`), а не голыми плейсхолдерами.

Зачем: пресеты — заключительная, самая заметная часть T-172, то, ради чего вообще затевался переход от «собери экран руками» к «опиши экран через компоненты». Часть архитектурного рефакторинга v4 (`.claude/rules/application-screen.md`), Linear T-172.

## Исправлен баг: подложка Screen.Header ничего не блюрила

`Screen.Content` изначально имел собственный `overflow-y: auto` — независимый скролл-контейнер. Но `Content` — это *сосед* `Header`/`Sidebar` в CSS-гриде, а не их предок, а `position: sticky` активируется только относительно скроллящегося **предка**. Из-за этого `Header`'s sticky-позиционирование и его `backdrop-filter: blur()` были тихо нерабочими — блюрить было нечего, ничего не проезжало «под» хедером при скролле. Заметнее всего это было видно в `Screen.DataView`.

Исправлено: `Content` больше не скроллится сам по себе — скроллится весь `Screen` целиком, естественным скроллом страницы/вьюпорта, без искусственного внутреннего скролл-контейнера. Теперь и `Header`'s sticky+blur, и `Sidebar`'s `height: 100vh` + sticky-пиннинг реально работают, как и задумывалось.

Заодно нашлась и исправлена вторая, независимая проблема в трёх из восьми новых сторей (`ListDetail`, `Form`, `DataView`): `Toolbar.Leading`/`Toolbar.Center` использовались напрямую внутри `Screen.Header` без обёртки в сам `<Toolbar>` — без него позиционирующий контейнер (`position: relative`, `height: 56px`) отсутствовал, и `.Leading`/`.Center` (оба `position: absolute`) не имели точки отсчёта.

Зачем: `position: sticky` — тонкая штука, которая молча не работает, если скроллящийся элемент не является предком того, что должно «прилипать» — этот баг было легко не заметить именно потому, что он не бросает ошибку, а просто визуально ничего не делает. Часть архитектурного рефакторинга v4 (`.claude/rules/application-screen.md`), Linear T-172.

## Реализован Screen.Sidebar.collapsed + сайдбар во всех app-shell пресетах

`Screen.Sidebar` получил проп `collapsed?: boolean` (контролируемый, чисто презентационный) — схлопывает grid-колонку сайдбара без размонтирования, так что внутреннее состояние сайдбара (скролл списка и т.п.) переживает переключение. Механизм: `.Screen:has(> .Sidebar.Collapsed) { grid-template-columns: 0 1fr; }` с `transition` на базовом правиле `:has(> .Sidebar)` — анимируется, поскольку оба значения `grid-template-columns` совместимы по типу треков.

Пять app-shell пресетов (`ListDetail`, `Dashboard`, `Form`, `Settings`, `DataView`) — до этого не все имели `Screen.Sidebar`, а `Toolbar.SidebarToggleAction` (сделанный ещё в рамках экшенов тулбара) вообще нигде не был показан в деле. Теперь все пять демонстрируют полноценный app shell: `Screen.Sidebar` + `Screen.Header` вместе, с `SidebarToggleAction` реально подключённым к `collapsed` через общий локальный стейт — не просто присутствующим, а работающим. `Auth`/`Empty`/`Error` остались без chrome — так и было решено для этой тройки.

Зачем: без `collapsed` кнопка-тоггл в тулбаре была бы чисто декоративной (меняла бы только свою иконку, ничего не скрывая), а разрозненные пресеты без сайдбара недостаточно показывали, для чего вообще нужна связка `Sidebar`+`SidebarToggleAction`. Часть архитектурного рефакторинга v4 (`.claude/rules/application-screen.md`), Linear T-172.
