# Dark Theme

- Current approach (JS state → data attribute, not relying solely on `prefers-color-scheme`) is confirmed correct — matches the next-themes/Radix Themes convention. Keep it.
- **Fixed**: the legacy `.AltroneDark` class selector is gone. `AltroneApplication` no longer sets it (neither the `classList.toggle` nor the `clsx` flag) — only `data-altrone-theme` remains, set on both the component root (`data-altrone-root` element, via React) and on `<html>` (via `useLayoutEffect`, for global non-scoped styles like `::selection` and for portals outside `data-altrone-root`). The dead ~30-variable block the ticket referenced (old names like `--headingTextColor`) no longer existed in `altroneApplication.module.scss` by the time this landed — already cleaned up separately at some point.
- **Found while migrating the selector**: the 6 real component files still using `.AltroneDark` (`NavigationList` group/link action, `Popover`, `Select`, `DataTable` header/filtering) were all referencing `var(--default-N)`/`var(--primary-N)`/`var(--danger-N)` (Tailwind-scale numeric names, 50-900) — variables that only ever existed in `core/src/components/application/index.css`, which **is never imported anywhere in the app**. Their dark-mode (and in places light-mode) colors were already no-ops. Same root cause found in `Calendar`, `ColorPicker`, `FilePicker`, `Range`, `DatePicker`, a Popover story, and a shared Storybook helper — all fixed to use real tokens (`--text-*`, `--background-*`, `--interactive-*`, `--accent-N`, `--danger-text-1`, `--disabled-text-color`). Since these tokens already auto-theme (the underlying `--gray-N`/hue scales redefine themselves under `[data-altrone-theme='dark']`), most of these no longer need a separate dark-mode block at all — one role-based declaration covers both themes.
- **Implemented**: FOUC blocking script — `getThemeInitScript(initialTheme)` (`core/src/components/application/getThemeInitScript.ts`) returns the script source; `AltroneApplication` renders it inline as the first thing in its own output. It replicates `resolveInitialTheme`'s logic (explicit `theme` prop wins; `'auto'` resolves via `matchMedia`) and sets `data-altrone-theme` on `<html>` before the rest of the tree paints. This is best-effort, not a guarantee, in a component library not tied to one SSR framework — for a hard guarantee in streaming SSR, a consumer should render `getThemeInitScript()` in their own document `<head>` instead.
- **Decided: not adopting `light-dark()`/`color-scheme`.** Rewriting every color file (10 hues + status + categorical, all built and actively maintained this session) onto `light-dark()` was judged too large a risk for an architectural-cleanliness win with no functional benefit — current per-file `[data-altrone-theme='dark']` duplication stays.
- `getThemeInitScript`, and the `Theme`/`Accent`/`Language` types, are now exported from the public API (`core/src/components/application/index.ts`) — they existed before but weren't reachable by a consumer.
- See `core/src/components/application/styles/DarkTheme.stories.tsx` (Storybook `Foundations/Dark Theme`) for an overview with a live theme-toggle demo.
