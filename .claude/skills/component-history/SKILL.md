Аргумент — название компонента (например, `Application`). Если не передан, спроси.

Формат страницы и директивы описаны в `.claude/rules/docs-tabs.md` (раздел `history`) и `.claude/rules/docs-dsl.md` (раздел «Release block») — прочитай их перед работой, здесь только порядок действий и решения, принятые при разборе.

## Порядок работы

1. Найди в `changelogs/release-history.md` раздел компонента (`## Имя`): прозу и блок «История по версиям». Для переименований смотри вводную часть файла.
2. Убедись, что у компонента есть страница-папка `docs/content/{en,ru}/<slug>/` (`index.md` и т.д.). Если страница пока одним файлом — переведи её в папку, `<slug>.md` → `<slug>/index.md` (см. `docs-tabs.md`). Не трогай остальные вкладки.
3. Создай `history.md` сразу в обеих локалях (`en` и `ru`) с одинаковой структурой. Английский — перевод русского источника.
4. Вкладка `history` уже зарегистрирована в `docs/lib/docTabs.ts` и `docs/components/DocTabs.tsx` — повторно ничего добавлять не нужно.
5. Проверь через `curl localhost:3000/{en,ru}/components/<category>/<slug>/history` (dev-сервер обычно уже запущен, не перезапускай). Если правка парсера не подхватилась — `touch` изменённого файла в `docs/lib/parser/`. Скриншот в браузере — по возможности.
6. Ничего не коммить, пока не попросят.

## Структура страницы

- Только `# Название` — **без вступления**. Версия, в которой компонент появился, — это самый старый `:::release`-блок; в нём строка `**X.0**` с одним пунктом о появлении компонента (см. ниже).
- По одному `:::release[...]` на **мажорную** версию, от новой к старой. Идущие подряд блоки парсер сам оборачивает в вертикальный `Flex` без gap — вручную не группируй.
- Заголовки блоков (кодовые имена релизов), `icon` в заголовке и `image` слева (для 1–3):

  | Мажор | Заголовок | `icon` |
  | ----- | --------- | ------ |
  | 4 | `Altrone 4 Decent Dragon` | `/logos/altrone-4.png` |
  | 3 | `Altrone 3 Curious CatZilla` | `/logos/altrone-3.png` |
  | 2 | `Altrone 2 Blind Basilisk` | `/logos/altrone-2.png` |
  | 1 | `Altrone 1 Angry Acromantula` | `/logos/altrone-1.png` |

  Показывай только те мажоры, в которых у компонента что-то менялось или с которых он появился. Раскрыт (`open="true"`) только актуальный мажор (4), остальные свёрнуты; если у компонента нет записей в 4 — раскрытых нет.
- Логотип слева: для версий 1–3 — `image="/logos/altrone-N.png"` (иллюстрация релиза самого Altrone, та же, что в `icon`); для версии 4 — `logo`, имя экспорта из `altrone-ui/logos` (текущий логотип компонента, лежит в `core/src/logos/index.ts`). Если в `docs/public/logos/` есть `<компонент>-<версия>.png` (например `text-2.png`) — используй его как `image` для этой версии; сначала посмотри содержимое папки. Если для версии логотипа нет (например, у компонента в старых версиях был другой облик или он не имел логотипа) и это не Application-случай с иллюстрациями релиза — не указывай ни `logo`, ни `image`: блок покажет серую заглушку с общей иконкой.
- `name` — как компонент назывался **в этой версии**. Пример: `Application` в 4, `AltroneApplication` в 1–3. Для других компонентов бери старые имена из вводной части `release-history.md` (`FloatingBox` → `Popover` и т.д.). Точная версия переименования часто неизвестна — не выдумывай, при сомнении спроси.
- Внутри блока: жирная строка минорной версии (`**4.0**`, `**2.1**` — не патч; патч-фиксы вливаются в свою минорную версию), под ней маркированный список изменений. Без заголовков внутри блока.

## Как писать пункты

- **Версия, в которой компонент удалили** — не перечисляй, что именно убрали (хуки, типы, константы), и не пиши, чем заменить. Один пункт красным текстом: `- :removed[Компонент удалён.]` (en: `The component was removed.`) — директива `:removed[...]` описана в `docs-dsl.md`.
- **Версия, в которой компонент появился** — один пункт: компонент добавлен в библиотеку и кратко для чего он нужен. Никаких фиксов, доработок, новых пропов и прочих деталей этой же версии — для пользователя они не имеют смысла, компонент для него новый. Детали пишем только в последующих версиях. Найди версию первого появления в источнике (если компонент был и раньше, чем упомянут в «Истории по версиям», — это самая старая версия из «Учтённых релизов», обычно 1.0; при сомнении спроси) и обязательно покажи её отдельной строкой. (Если компонент появился в 4.0, а других записей у него нет — в блоке будет ровно один пункт.)
- Одна строка — одно изменение, коротко, в терминах API (`asChild`, `persistTheme`, проп `icons`). Что добавили / изменили / удалили.
- **Не пиши** причины и оценки («мёртвый код», «стал чистым корнем-провайдером») и внутреннюю архитектуру — только то, что заметит пользователь библиотеки.
- Перечисляй конкретно: языки — названиями (китайский (упрощённый), португальский, турецкий), а не кодами; исправление кодов языков можно упомянуть отдельной фразой.
- Названия из кода (`Altrone`, `AltroneApplication`, пропы, хуки) остаются в `` ` `` и не переводятся. Примеры кода и демо — всегда на английском в обеих локалях.
- Если в `release-history.md` версия названа иначе, чем в пользовательском описании (например, фикс относится к `Altrone`, а компонент уже переименован в этой версии) — следуй решению пользователя по имени в блоке, а формулировку пункта из источника не подменяй без спроса.
